# Task 7 rev 2: MarkRenderer, Renderer, IRenderer

Written 2026-08-28, after auditing what the interrupted Task 7 session left
behind. Supersedes the Task 7 section of
`docs/plans/2026-08-28-mro-phase0-rendering-spike-rev2.md`. Everything else in
that plan stands.

## Why this task, and why it needs re-planning

Task 7 assembles the image and the JSON. It is where the size budget is finally
decided, and nothing after it can start until it lands: Task 8 wraps it in a
token contract, Tasks 9 to 11 deploy that contract, and Task 12 turns the
numbers into a go / no-go on the whole spike.

The previous session did the research and the pre-flight probe, then stopped
before writing any Solidity. The probe was the right first move and it earned
its keep: it found that the wrapper costs more than the remaining budget, so
building MarkRenderer first would have meant building it twice.

This revision exists because the probe's answer changes the order of the work.
The ring cap has to be settled before any Mark code is written, and settling it
needs a decision from the operator.

## What the probes established

All figures are the complete `tokenURI` for one token, measured 2026-08-28
under `via_ir`, against the 2,000,000 gas / 20,000 byte HARD limit.

### The encoding is settled

Three routes for the same token at 80 rings:

| Route | Bytes | Gas |
|---|---|---|
| base64 SVG inside a utf-8 JSON | 14,780 | 2,375,511 |
| utf-8 SVG, percent-escaped | 11,139 | 5,846,742 |
| base64 SVG inside a base64 JSON | 19,804 | 3,210,443 |

Base64 the SVG, serve the JSON as plain utf-8. It wins on gas by a factor of
2.5 because a per-byte escape loop in Solidity costs far more than Solady's
word-wise encoder. The spec left this open pending the spike; the spike has
answered it.

### The Marks are nearly free

Measured at one ring, each Mark against a bare token:

| Mark | Gas delta | Bytes |
|---|---|---|
| Vein | -196 | +6 |
| Halo | +5,193 | +6 |
| Voice | +5,657 | +83 |
| Crown | +7,134 | +7 |
| Bloom | +13,141 | +219 |
| **All five together** | **+16,736** | **+325** |

Vein measures marginally negative because it substitutes one colour string for
another of the same length; the difference is measurement noise, not a saving.

This is the good news in the task. The Marks are colour substitutions into
paths that already exist, not new geometry, so they cost almost nothing. The
budget problem is entirely the rings.

### The rings are the whole problem

Full `tokenURI` with all five Marks worn, which is the worst case a token can
actually reach:

| Rings | Gas | Bytes |
|---|---|---|
| 30 | 1,916,754 | 12,515 |
| 33 | 1,944,990 | 12,659 |
| 35 | 1,967,344 | 12,755 |
| 37 | 1,989,778 | 12,851 |
| **38** | **2,001,062** | 12,899 |
| 40 | 2,023,683 | 12,995 |
| 80 | 2,459,786 | 15,695 |

The hard limit breaks between 37 and 38 rings. Bytes are never the constraint:
even at 80 rings the URI is 15,695 against a 20,000 limit.

`MAX_RINGS` is currently 80. As it stands the contract can render a token that
exceeds the gas limit, so this must be resolved in this task and not deferred.

### Where the ring cost actually lives

Splitting the two halves, because the fix differs by half:

| Rings | Frame and rings | Code block |
|---|---|---|
| 1 | 458,969 | 706,458 |
| 20 | 596,264 | 712,414 |
| 40 | 730,622 | 712,414 |
| 80 | 1,001,486 | 749,285 |

From 1 ring to 80, the frame renderer grows by 542,517 gas and the code block by
42,827. **Ninety-three per cent of the ring cost is the frame renderer's own row
loop**, not the larger canvas pushing coordinates up a digit.

That matters, because it means the cost is probably recoverable. Rings are
currently OR-ed into the same per-row bitmap as the frame and emitted by
`PathWriter`, so every added ring makes the canvas taller and every row scan
wider, and the whole loop runs over `51 + 2 * rings` rows. The ring cells
themselves are trivial geometry: concentric one-cell outlines.

## The decision this task needs from the operator

**How many years of return visits does the artwork draw a ring for?**

Two framings matter before choosing.

First, **the cap limits the rings, not the record.** The `Years` attribute in
the JSON is unbounded and keeps counting whatever the cap is. A token past the
cap still records every year; it just stops adding a new outline for each one.

Second, **no token will plausibly reach any of these numbers.** Thirty rings is
thirty years of an agent checking in. The cap is a statement about what the
piece promises, not a number anything will hit.

The options:

| Option | Cap | Gas at cap | Left for Task 8 |
|---|---|---|---|
| A | 80, after rewriting ring emission | to be measured | to be measured |
| B | 30 | 1,916,754 | 83,246 |
| C | 25 | 1,878,185 | 121,815 |
| D | 20 | 1,820,891 | 179,109 |
| — | 37 | 1,989,778 | 10,222 |

37 is the arithmetic maximum and is not a real option: Task 8 adds the ERC-721
wrapper and the `SLOAD`s for the token state, including six words for the
172-byte code, and 10,222 gas does not cover that.

**Recommendation: try A, fall back to B.**

Attempt the cheaper ring encoding first, because the measurement says most of
the 542,517 is in how rings are drawn rather than in the fact of drawing them.
Emit each ring as its own stroked `<rect>` instead of merging it into the row
bitmap, which replaces a growing per-row bit scan with about 60 bytes of string
concatenation per ring.

This is a measured experiment with a fixed budget, not an open-ended
optimisation: implement it, measure it, and if 80 rings does not then fit under
1,900,000 with all Marks worn, stop and take option B. The cap is set in that
same step either way, and the task moves on.

The cost of trying is roughly half a day. The trade-off against going straight
to B is that B is certain and available now, and A might return the full 80.

**This is the judgement call I need from you before I start.** Everything after
it is mechanical.

## Six defects to fix along the way

The interrupted session left working but unfinished code. These are folded into
the steps below rather than left as a cleanup pass.

1. **Voice and Bloom have no test.** The JS Mark test loops
   `["vein","halo","crown"]`, the three that already existed. I verified the two
   new ones decode at 900, 700, 500, 350 and 250 px with the duotone intact, but
   nothing in the suite would catch a regression.
2. **The quiet-zone tint claim is unevidenced.** The comment in
   `tools/render-token.mjs` states that `#f9eaef` is the deepest tint that
   decodes and `#f7e3e8` fails at 700 and 500 px. Neither value appears anywhere
   else in the repo. That was the sweep the 2026-08-28 OOM killed. Either back it
   with a test or delete the claim.
3. **The JS renderer never applies a lapse.** `renderSvg` calls
   `tierColour(streak)`. `lapsedColour` is exported and unit-tested in isolation
   but never reaches the image, while the Solidity side calls `Palette.lapsed`.
   On any lapsed token the two renderers disagree on both the heart and the frame
   colour.
4. **Dead line.** `const streakNow = resting ? streak : streak;` has identical
   branches, so the "a resting token freezes" comment above it describes
   behaviour that is not implemented.
5. **The probe's `tokenURI` is not a valid reference.** It writes a raw `#` in
   the token name, which truncates the JSON at the URI fragment; the JS side
   writes `%23` and its own comment records the failure. The description strings
   also differ between the two. Harmless for gas, but `Renderer.sol` cannot be
   copied out of it.
6. **`TokenView` has no `parent` field** that the spec's attribute list wants.
   Emit what the struct holds and raise the gap for Task 8 rather than inventing
   a value.

## Steps

1. **Settle the ring cap.** If option A: change ring emission in
   `FrameRenderer.sol` to stroked rects, keep `tools/render-token.mjs` in step,
   re-run the sweep, and decode-check a ringed token at five pixel sizes because
   `shape-rendering="crispEdges"` and half-pixel strokes interact. If the result
   does not fit under 1,900,000 at 80 rings with all Marks, revert to option B.
   Set `MAX_RINGS` in **both** `FrameRenderer.sol` and `tools/render-token.mjs`
   to the chosen value; they must not drift. Update `RingCurve.t.sol` to assert
   the new cap.

2. **Fix the JS reference first**, because it is the thing Solidity is diffed
   against and a wrong reference makes a green differential test meaningless.
   Defects 3 and 4: route `lapsedColour` into `renderSvg` so the image pales, and
   either implement the resting freeze or drop the dead line and its comment.
   Defect 6: emit the attributes the struct actually holds.

3. **Cover the JS Marks.** Extend the existing Mark loop to all five renderable
   Marks plus the all-five combination, asserting each changes the image, still
   decodes via `scanResult` at several pixel sizes, and keeps the destination.
   Defect 2: add a test that pins the quiet-zone tint floor with a real decode, or
   remove the claim from the comment. Keep the sweeps small and run them under
   `~/scripts/safe-build.sh` per the 2026-08-28 incident.

4. **Write `MarkRenderer.t.sol` first, then `MarkRenderer.sol`.** Per the plan's

   falls below 4.5:1. The probe already shows this is mostly colour selection --
   `FrameRenderer.paths` and `CodeRenderer.paths` already take the colours as

5. **Write `Renderer.t.sol` and the differential test, then `Renderer.sol` and

   Do not read `tools/out` via `vm.readFile` as the original plan says -- that

6. **Delete the three probes** once their numbers are in
   `docs/phase0-results.md`: `B64Probe.t.sol`, `WrapperProbe.t.sol`,

7. **Record and commit.** Update `docs/phase0-results.md` with the encoding

   `forge build --sizes` are all green.

## Trade-offs and what cannot be undone

- **Lowering `MAX_RINGS` is a visual promise, and changing it later changes
  every token's image.** The renderer is swappable by design, so it is not
  literally permanent, but a token that has been displaying 40 rings and then
  shows 30 is a visible rewrite of somebody's record. Choose the number now.
- **Option A touches a renderer that is currently green and byte-for-byte
  verified.** It is guarded by the existing differential tests, so a mistake
  shows up as a failure rather than as silent drift, but it is a rewrite of
  working code and that is the risk being taken for the extra 50 years.
- **Nothing here is irreversible and nothing spends funds.** No operator-manual step
  is required in this task. The next one that needs you is Task 9's faucet
  funding.

## What this task deliberately does not build

Pulse's `animation_url`. The spec wants an on-chain `data:text/html;base64` page
carrying a second copy of the SVG plus a SMIL animation, which roughly doubles
tokenURI bytes. Phase 0's job is the static image. It gets measured separately
and reported before anything is decided.
