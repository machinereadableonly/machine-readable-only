Scope: contracts/src/MachineReadableOnly.sol and contracts/src/Ladder.sol at commit a98c08c, read against docs/specs/2026-09-02-mro-mark-ladder-design.md (the ladder authority) and section 7 of the master spec. Two structural facts frame everything below, and both are good news. The contract never holds or moves value. 12.1 A sold token stays under the seller's key until the buyer rebinds, and the seller can permanently close a Mark pair on it

Severity: High

contracts/src/MachineReadableOnly.sol:480-528 (applyMark) and :598-633 (seed), with warden/src/mcp/tools/upgrade.mjs:44 and warden/src/mcp/tools/seed.mjs:30.

applyMark consults neither _ownerOf(id) nor _agentKeyOf[id]. Its only access control is onlyWarden. The same is true of seed, which reads _tokens[parentId] and _agentKeyOf[parentId] and never asks who owns the parent. So the entire binding between "who may change a token" and "who owns it" lives in the Warden -- and the Warden binds on the key, not the owner: if (token.keyId !== ctx.keyId) return { ok: false, reason: "not-bound-to-caller" }. _agentKeyOf is changed only by rebind (:558), which is onlyTokenOwner and is not triggered by a transfer.

Failure scenario, in order:

  1. Alice mints token 1 bound to her agent key K, and checks in for a year. Token 1 reaches level 400 with a 400-day run.
  2. Alice sells token 1 on a secondary marketplace. ERC721._update is not overridden, so the transfer touches nothing else: _agentKeyOf[1] is still K, and Alice still holds K.
  3. Bob now owns token 1 and has not called rebind (nothing on chain, and nothing in the transfer, prompts him to).
  4. Alice's agent signs at the door with K, calls upgrade for Mark 8 (Break, earned, minStreak 365, free). The Warden's key check passes because the chain still says token 1 is bound to K. The Clock calls applyMark(1, 8, 0). Bit 8 is set in _marks[1].
  5. Ladder.sol:31 gives Vessel (Mark 7) excludes = 1 << 8. Bob can now never buy Vessel on token 1. There is no removeMark and no upgrade path, so this is permanent.

The same key also lets Alice call seed from Bob's token, minting a child to an address of her choosing and consuming K's seed budget, and lets her keep credited days flowing to Bob's token via checkin (warden/src/mcp/tools/checkin.mjs:31). The seed case is the one where she gains an asset she does not own the parent of.

Cheap variants of the same move need no maturity at all: Ache (Mark 2) needs a 7-day run and forecloses Hush; Beat (Mark 4) needs 30 and forecloses Static; the earned Iris (Mark 6) needs 100 and forecloses the bought Iris. The Vessel case is the expensive one at $1,250 forfeited, and it needs a 365-day run, which is exactly the kind of token that would command a secondary price.

This is not the accepted rebind trust boundary. That boundary (CLAUDE.md, spec section 7) is about a token owner pointing a token at another key's seed budget. This is the mirror image: a key holder exercising authority over a token it no longer owns, and the accepted boundary's stated mitigation ("the Warden re-checks the signature against the current on-chain binding") is the very mechanism that lets it through, because the binding did not move when the token did.

What to do. No contract change is possible or needed, which matters given the contract is permanent. Fix it in the Warden: for upgrade, seed and rest, require the current on-chain ownerOf(id) to match the owner recorded at the last mint or rebind, and refuse with a reason that tells the caller the token has changed hands and must be rebound. State the rule in llms.txt and the raw protocol doc so a buyer knows rebind is the first call after a purchase, not an optional one. If the Warden cannot be made to refuse, the agent-facing copy must say plainly that buying a token does not transfer control of it.

12.2 One compromised owner key can permanently deface the whole collection, and pause() is no defence against it

Severity: Medium

contracts/src/MachineReadableOnly.sol:174 (setWarden), :467-473 (setUpgrade), :186-187 (pause / unpause), :480-528 (applyMark).

The project already reasoned about defacement: the spec's applyMark row records that whenNotPaused was added because "mark bits are unclearable and a compromised Warden could otherwise deface every token while the contract read as paused". That mitigation covers Warden-key compromise only. The owner key walks around it in three calls.

Failure scenario:

  1. Attacker obtains the owner key. pause() and unpause() are both onlyOwner, so the emergency control is now the attacker's.
  2. setWarden(attacker) at :174. Warden and owner are separate addresses on chain today (CLAUDE.md records the separation), but nothing stops the owner collapsing them.
  3. setUpgrade(i, u) at :467 for each id 1..10, with excludes = 0, requiresAny = 0, minLevel = 0, minStreak = 0, requiresWhole = false. Only sold is preserved (:469-471); every gate is a plain overwrite, and nothing on chain checks the stored record against Ladder.all().
  4. applyMark(id, 1..10, variant) for every minted id. Every token now wears every Mark, including both sides of every pair. _marks has no clearing path, mint does not reset it, and there is no upgrade path.

The distinguishing facts, versus "the owner of an NFT contract is trusted": the damage is irreversible (no removeMark, no proxy), it destroys the exact property the piece sells (that a Mark records something that happened), and sunset() does not help because it only blocks future writes.

Verifier: the sunset() sentence is wrong. applyMark carries notSunset (:484) as well as whenNotPaused, and isSunset is written true only at :206 and never false anywhere. So a defender who reaches sunset() first permanently stops the defacement, and the attacker cannot undo it even holding the owner key. Blocking future writes IS the defence here, because the damage is entirely future writes. Resting tokens are also immune (:500). The three-call chain itself is real and the rest of the finding stands.

The one mitigating fact is that ownership is transferable: Ownable2Step is intact (renounceOwnership reverts at :196-198, but transferOwnership / acceptOwnership work, pinned by Bounds.t.sol:215). So this is remediable at any time.

What to do. Make the mainnet owner a 2-of-3 Safe (or an equivalent hardware-backed multisig) rather than the deployer EOA, and do it before or immediately after the permanent deploy. Separately, commit a post-deploy verification script that reads all ten upgradeOf(i) records back off the chain and asserts they equal Ladder.all(); CLAUDE.md records that this was checked by hand on Sepolia on 2026-09-03, but nothing in the repository re-runs it, so a silent setUpgrade would not be noticed.

12.3 level and streak are fully backfillable by the Warden in a single transaction, so the ladder spec's "cannot be forged" claim is narrower than it reads

Severity: Medium

contracts/src/MachineReadableOnly.sol:310-336 (the batchCheckIn loop, in particular the streak rule at :330) and :521 (Mark 6 writing the run).

Section 4.4 of the ladder spec says of the earned Iris: "The contract writes it from _tokens[id].streak at apply time. The Warden does not supply it, so it cannot be forged: the piece can claim it as a fact rather than as a promise, which is exactly the class of claim the cold readers said they would go and check." The code does read s.streak at :521, so the narrow claim is true. But s.streak is itself entirely Warden-written, and batchCheckIn accepts the same id many times in one call with ascending days (the spec's own row calls this legal, for late writes after an outage). There is no per-transaction and no per-day limit.

Failure scenario:

  1. Attacker holds the Warden key for one transaction (the Clock's key on the VPS is the single point).
  2. Attacker calls batchCheckIn with token id X repeated for every day in (lastDay, today()]. Each iteration passes day > tday (:325) and day <= s.lastDay (:326), increments level, and because each day is exactly lastDay + 1 the streak increments too (:330).
  3. A token that has existed for over a year but checked in rarely now reads level 400, run 400, in one block.
  4. Attacker then calls applyMark(X, 8, 0) -- Break, minStreak 365, free -- or any other earned Mark, and seed if the key's tenure allows.

The reassuring half, which should be stated alongside it. The forgery is bounded. Every credited day consumes a distinct day index in (lastDay, today()], and lastDay starts at mintDay, so level can never exceed today() - mintDay + 1. A Warden cannot manufacture a 365-day run on a token minted last week. What it can manufacture is diligence on a token that is genuinely old.

What to do. No contract change (and none is possible). Correct the claim: section 4.4 of the ladder spec, and any agent-facing copy derived from it, should say the run cannot be forged by the agent, and that its ceiling is the token's own age. Then treat the Clock's key custody as the control that actually backs the claim, which is section 15's ground.

12.4 applyMark never bounds upgradeId; it relies entirely on setUpgrade being the only writer of _upgrades

Severity: Low (hardening; not reachable today, verified)

contracts/src/MachineReadableOnly.sol:486-489, against the guard at :468.

applyMark computes uint256 bit = 1 << upgradeId (:489) with upgradeId straight from calldata and no range check. The contract's own comment at :426-430 names the consequence exactly: an id of 16 would alias the Iris shape bits at 16-17 and corrupt every token's variant. The defence is indirect -- the comment says "Refused where the record is written, so the bad record cannot exist", and setUpgrade (:468) does refuse ids 0 and above 10.

I verified the indirection holds: _upgrades is written in exactly one place, setUpgrade at :470-471 (grep over the file returns :74 declaration, :460 read, :469-471 write, :486 read). So _upgrades[16].active is false for every out-of-range id, and applyMark reverts MarkInactive before reaching the shift. There is no exploit path today.

The reason to raise it anyway is that the contract is permanent and the invariant is one edit away from being wrong, while the direct check is a single comparison identical to the one already at :468. A future setUpgrade variant, or a batch setter added in a redeploy of this design, reintroduces it.

What to do. If any further change to this contract is ever made before the mainnet deploy, add if (upgradeId == 0 || upgradeId > MAX_MARK_ID) revert MarkIdOutOfRange(upgradeId); as the first line of applyMark. If the contract is frozen as-is, record in the source comment that the bound is enforced only at setUpgrade and that _upgrades must never gain a second writer.

12.5 rebind accepts bytes32(0), the exact value mint refuses

Severity: Low

contracts/src/MachineReadableOnly.sol:558-562, against :251-254.

mint rejects a zero key with a two-line comment explaining why: "A Warden serialising a missing thumbprint to zero would burn the zero key permanently AND create a shared seed budget that any token owner could rebind into for free." rebind writes _agentKeyOf[id] = newKeyId at :559 with no such check.

I traced the seed-budget half and it is safe: seedsAvailable (:588-595) returns 0 for key zero, because _firstMintDay[0] == 0 and _hasMinted[0] == false, and neither can ever be set now that mint refuses the zero key. So the on-chain consequence of rebind(id, bytes32(0)) today is only that the token can no longer be seeded from, which the owner can undo with another rebind.

The residual scenario is cross-layer, and it is the mirror of the bug mint's guard was written against. If the Warden ever serialises a missing or malformed thumbprint to 0x00..00 when comparing against the chain, a token deliberately rebound to zero would match a request carrying no valid key. That is a Warden question (section 13), but the contract is the half that permits the state to exist.

What to do. Have the Warden refuse a rebind request whose target key serialises to bytes32(0), and assert in warden/test/ that keyIdToBytes32 can never return zero for any input it accepts. Note in the source comment at :555-557 that the zero key is legal here and why that is safe.

12.6 _setRenderer accepts any non-zero address, including an EOA, and a bad renderer bricks tokenURI collection-wide

Severity: Low

contracts/src/MachineReadableOnly.sol:211-215 and :159-162.

The scope question was whether a malicious or broken renderer can do more than return bad bytes. It cannot, and that is worth recording as a positive result: IRenderer.tokenURI is declared external view (contracts/src/render/IRenderer.sol), and MachineReadableOnly.tokenURI is public view, so solc compiles the call as a STATICCALL. The renderer cannot write storage, cannot reenter any write path, and no write path calls it at all -- IRenderer appears exactly once in the contract, at :161. So a renderer cannot make mint, batchCheckIn, applyMark, seed, rebind or rest revert.

What it can do is make every tokenURI call revert or run out of gas. _setRenderer only checks r != address(0) (:212). Setting it to an EOA, or to a contract with the wrong ABI, leaves every token's metadata unreadable until the owner sets it again. MachineReadableOnly.t.sol:42-51 covers the happy path and the zero rejection, but nothing covers a non-contract address.

What to do. Since the contract is frozen, make it a deploy and operations rule rather than a code change: any setRenderer transaction must be preceded by a cast call <new> "tokenURI((uint256,...))" against a real token id, and test/ should gain a case asserting the current renderer answers for a minted token after any renderer swap script runs.

12.7 A hostile mint recipient can burn the operator's gas through the _safeMint callback, and the documented pre-flight does not catch it

Severity: Low

contracts/src/MachineReadableOnly.sol:272 (mint) and :630 (seed).

Spec section 7 records the known _safeMint hazard and its mitigation: "The Warden therefore pre-flights the to address before charging: if it has code and does not answer the ERC-721 receiver interface, refuse the mint with a plain reason instead of taking the fee and reverting."

That pre-flight is a static probe. A receiver that answers it correctly and then consumes all remaining gas in the real call -- or that branches on msg.sender being the token contract, or on gasleft() -- passes the probe and bombs the transaction.

Failure scenario: an agent passes the door, requests a mint, and nominates a contract it controls as to. The Clock builds and sends the mint transaction. onERC721Received loops until the gas is gone. The transaction reverts having consumed its whole gas limit, paid by the operator's Clock wallet. The agent pays nothing (the refusal-cancels-settlement fix of 53ed350 returns the USDC) and can repeat.

The cost is small in absolute terms -- a 16.7M gas transaction at Base's 0.006 gwei floor is well under a cent -- so this is a nuisance and a wallet-drain irritant, not a funds risk. It is worth naming because the mitigation is already written down and does not actually cover the case.

What to do. Cap the gas the Clock sends on a mint or seed transaction rather than letting it use the block limit, and record repeated failures against the same to address so the Warden can refuse it. Amend the spec's pre-flight sentence so it does not claim more than it delivers.

Verifier: the gas-burn half is refuted; the pre-flight half is confirmed and understated. warden/src/clock/write.mjs:116 runs simulateContract FIRST, so a receiver that reverts or exhausts gas fails the simulation and no transaction is broadcast at all. :131-137 then estimates gas separately and refuses above MAX_TX_GAS (15M), passing the estimate explicitly -- the Clock never sends the block limit, so the "16.7M gas transaction" cannot occur, and the remedy is already implemented. "The agent pays nothing" is also wrong: mint.mjs:106 returns ok: true and the payment settles before the Clock ever writes. What survives is worse than the hostile case: greps for onERC721Received, 0x150b7a02 and receiver across warden/src/ find nothing, so the spec's pre-flight is not implemented AT ALL. A BENIGN non-receiver to -- a bespoke smart account -- is charged 1 USDC, told ok: true with an onChainBy promise, and then sits in pendingMints() forever while run.mjs:151 alerts a human. That is paid-and-never-delivered.

12.8 The three ladder exclusion tests recompute Ladder.sol's own expression, so a shared truncation bug would pass all three

Severity: Low (test integrity; the masks are in fact correct, verified)

contracts/src/Ladder.sol:48 against contracts/test/Ladder.t.sol:29-60.

Ladder.sol:48 builds every mask as excludes: uint16(1 << excludes) where excludes is a uint8 parameter. Solidity gives a shift expression the type of its left operand, and a number-literal left operand takes its type from context, which is a documented sharp edge (Verifier: this premise is wrong for THIS expression. Measured on solc 0.8.35, uint16(1 << n) with n a uint8 variable gives 256 and 1024. A number literal does not truncate here; only an explicitly typed uint8 left operand does. The test-integrity conclusion below is unaffected and correct): had the literal been typed uint8, every 1 << n for n >= 8 would truncate to zero, and Ladder.sol:31 (Vessel, excludes 8) and :33 (Tint, excludes 10) would carry mask 0. Vessel would not be closed by Break, and Tint would not be closed by Aura -- the pair exclusivity that the entire ladder rests on.

All three exclusion tests would pass anyway:

  • test_everyExclusionIsSymmetric (:29) compares u[a].excludes & uint16(1 << b) against the mirror expression. All-zero masks are symmetric.
  • test_noExclusionCrossesAPairBoundary (:45) continues on a zero mask, so it asserts nothing.
  • test_eachMarkExcludesExactlyItsPartner (:54) asserts u[a].excludes == uint16(1 << partner) -- the identical expression to the one under test, so 0 == 0 passes.

The masks are correct. I confirmed it through the one test that does not recompute the implementation: test_theLadderMatchesTheJavascriptMirror (:184) pins keccak256(abi.encode(Ladder.all())) to a constant generated by tools/ladder-fixture.mjs, which encodes m.excludes from warden/src/mcp/ladder.mjs:35 (1 << partnerOf(id), a plain JavaScript number, 256 for id 7 and 1024 for id 9) as uint16. That test passes (forge test --match-path test/Ladder.t.sol, 10 passed), which is only possible if the Solidity masks equal the JavaScript ones.

So the safety net exists, but it is a single hash in a different language, and the three tests written specifically to pin this invariant cannot see it.

What to do. Add one literal assertion to Ladder.t.sol -- for example assertEq(u[7].excludes, 256) and assertEq(u[9].excludes, 1024) -- so the invariant is pinned by a value a human wrote rather than by an expression the implementation also uses.

12.11 rebind and rest sit outside both pause and sunset; the spec records the first and is silent on the second

contracts/src/MachineReadableOnly.sol:558 and :567.

[13] Door authentication -- findings

Scope: warden/src/door/verify.mjs, challenge.mjs, directory.mjs, middleware.mjs, plus warden/src/server.mjs, warden/src/main.mjs and warden/src/mcp/keyId.mjs. Read against the INSTALLED web-bot-auth 0.1.3 and its dependency http-message-sig 0.2.0 (warden/node_modules/http-message-sig/dist/index.mjs), not against the package names.

Six of the findings below were reproduced by running the door's own exported functions against the repository's own Ed25519 test vector. Where a claim is reasoned from the code rather than executed, it says so.

The headline: the door's cryptography is sound and its SSRF guard is the strongest part of this repository, but nothing in the service records that a signature has been used, and the two headers that were supposed to provide freshness are not covered by the signature at all.

13.1 One captured signed request is replayable, unlimited times, for up to five minutes

Severity: High

warden/src/door/verify.mjs:45 (REQUIRED), warden/src/door/middleware.mjs:82-85 (the challenge headers are read but never bound), warden/src/door/middleware.mjs:93 (sigHash is produced and never checked), warden/node_modules/web-bot-auth/dist/index.mjs:113 (the RFC 9421 nonce is copied into vparams and never validated or recorded).

Verifier: confirmed and independently reproduced. The web-bot-auth citation was :104 and is corrected to :113; :104 is the closing brace of the expires check, and nonce: params.nonce sits at :113 inside the vparams block at :108-114.

REQUIRED binds @authority, @method, @path, signature-agent and content-digest. It does not bind challenge or challenge-response, and there is no replay cache keyed on the signature, on params.nonce, or on sigHash. sigHash is computed at middleware.mjs:98 and passed straight through server.mjs:254 into credits.sigHash as a record; queries.mjs:85 inserts it and nothing ever selects on it for uniqueness.

Failure scenario, in order:

  1. An attacker obtains one signed request to POST /mcp -- the Signature, Signature-Input, Signature-Agent and Content-Digest headers plus the body bytes. The signature's expires is at most five minutes after created (verify.mjs:122), so the window is up to five minutes wide.
  2. The attacker reads keyid straight out of the Signature-Input header it is holding. It is plaintext there.
  3. The attacker sends any unsigned request and takes the fresh challenge out of the 401 body (middleware.mjs:63-64). This is free and unauthenticated.
  4. The attacker computes challenge-response = hex(SHA-256(challenge + keyId)) (challenge.mjs:83). Every input is in its hands.
  5. It replays the captured headers and body with the fresh challenge pair. Admitted. Repeat from step 3 as often as it likes until expires passes.

Demonstrated. Signing once and replaying four times against admit() with four freshly issued challenges gave four admissions with an identical sigHash (84e263d1b9a6...) and the correct keyId. The existing test at warden/test/door.test.mjs:147 ("the same challenge answer cannot be replayed") does not catch this, because its helper re-signs the request on each attempt: it pins the challenge burn, not the signature.

What the replay gets an attacker is bounded by whatever idempotency sits downstream, and that varies by tool. checkin is safe by construction -- the unique index on credits (tokenId, day) (warden/src/mirror/schema.sql:42) makes a repeat a no-op. mint and upgrade replay the same x402 payment authorisation, because the payment travels in the JSON-RPC _meta (warden/src/pay/x402.mjs:31) and is therefore inside the digest; whether the facilitator rejects the reused EIP-3009 nonce is Section 14's question, not this one, and this section does not claim it does. seed (warden/src/mcp/tools/seed.mjs:47) is a check-then-act on q.seedsSpent(ctx.keyId), which sequential replays would catch and concurrent replays might not.

The restart case in the protocol doc is a distraction. The doc (docs/2026-09-01-mro-raw-protocol.md, section 1) says the exposure a restart creates is that "a challenge captured in the preceding five seconds could in principle be replayed across it". That is true and it is the smaller problem. The signature is unrecorded whether or not the process restarts, so the real replay window is the full five minutes and does not depend on a restart at all. The doc's paragraph, read as written, tells an implementer that replay is a five-second edge case.

What to do. Use the RFC 9421 nonce that is already on every request and already parsed. Keep a set of (keyid, nonce) pairs, or of sigHash, swept on the same schedule as seen but at the signature window rather than the challenge window, and refuse a second presentation. It costs one Set of five minutes' traffic. Alternatively add challenge to REQUIRED, which binds the five-second freshness check to the signature and reduces the window to five seconds -- cheaper, but it makes every signature single-use only because the challenge is, so the nonce set is the more honest fix. Then correct the restart paragraph in the protocol doc.

13.2 Twenty thousand unauthenticated requests permanently close the only entrance for agents without a domain

Severity: High

warden/src/bootstrap.mjs:24 (MAX_TOTAL_KEYS = 10_000), warden/src/bootstrap.mjs:70 (if (q.keyCount() >= MAX_TOTAL_KEYS) return false), warden/src/door/directory.mjs:442, warden/src/server.mjs:163-166 and :220-222, warden/nginx.conf.example:41-50 (the origin lock is commented out).

The registration limiter is per-thumbprint by design, and that design is correct as far as it goes -- registerRoute charges the budget to a key the caller has just proved possession of (directory.mjs:442), so one caller cannot lock out another. But a fresh Ed25519 keypair is free, so the 20-per-minute window never binds an attacker who uses a new key each time. The only limit that applies to the aggregate is the 10,000-key total, and reaching it IS the attack: once q.keyCount() >= 10_000, every subsequent registration returns rate-limited forever. There is no eviction, no expiry on a stored key, and no operator route in the code to prune the table. On a permanent mainnet deployment that is a permanent condition absent manual database surgery.

Failure scenario, in order:

  1. The attacker generates 10,000 Ed25519 keypairs. Seconds of CPU.
  2. For each: GET /keys/nonce, sign the nonce's ASCII bytes, POST /keys. Two unauthenticated requests per key, 20,000 in total, no signature and no challenge needed on either.
  3. Every registration is accepted (each key's own budget is untouched) until the table holds 10,000 rows.
  4. From then on, every honest agent without a domain of its own gets 429 {"ok":false,"reason":"rate-limited"} and cannot get in at all. The only remaining route is hosting a JWKS on a domain, which is exactly the population POST /keys exists to serve.

The same 10,000 rows make the one public, unsigned, unmetered route expensive. GET /.well-known/http-message-signatures-directory (server.mjs:163-166) calls renderDirectory(q) on every request, which reads every row, JSON.parses each stored JWK and re-serialises the lot with two-space indentation (directory.mjs:300-303). Measured at 10,000 minimal Ed25519 JWKs: 11.8 ms of synchronous CPU and a 1,140,018-byte response per request, before the database read. That is roughly 85 requests per second to saturate one core of a single-process Node service with no worker threads, from an unauthenticated route. Separately, server.mjs:220-222 calls writeFileSync with that same 1.1 MB on every successful registration, blocking the event loop each time.

The protocol doc names the mitigation and it does not exist: "Rate limiting that is nginx's job, not this handler's" (docs/2026-09-01-mro-raw-protocol.md, section 2b). warden/nginx.conf.example contains no limit_req, no limit_conn and no client_max_body_size, and its one hardening measure -- the Cloudflare origin allowlist -- is commented out with a note that it is "NOT enabled at first deploy".

What to do. Three things, in this order. (a) Add limit_req on /keys and /keys/nonce in the nginx template, so the delegation the document already claims is real. (b) Cache the rendered directory in memory and invalidate it on registration, so a public GET is a string copy rather than a full table render, and give it an ETag. (c) Decide what happens at the 10,000 cap other than closing forever -- an expiry on keys never used to sign, or an operator prune command -- and write the answer down, because on a permanent deployment "we will fix it if it happens" is not available.

13.3 Naming a victim's Signature-Agent once locks that agent out for an hour

Severity: Medium

warden/src/door/directory.mjs:363-368 (the failure is remembered), :356-358 (a remembered failure is trusted for an hour), warden/src/server.mjs:89 (one cache, shared by every caller, for the life of the process).

makeLookup caches failures as well as successes, for the same one hour. The comment at :361-362 explains why that is there, and the reason is good: without it, every unauthenticated request naming an unreachable directory becomes one outbound request. But the cache key is the directory URL, which is derived from an unverified, attacker-supplied Signature-Agent header, and there is no invalidation path and no way for the affected agent to clear it.

Failure scenario, in order:

  1. The attacker picks a target agent that hosts its own JWKS at https://victim.example/.well-known/http-message-signatures-directory, and waits for, or causes, a moment when that host does not answer within the 3-second timeout. Any transient will do.
  2. The attacker sends one request to the Warden with Signature-Agent: "https://victim.example" and a junk Signature. It needs no valid key and no challenge: the lookup happens inside the verifier callback, before the signature is checked.
  3. The fetch fails. { failed: true, at: now } is written to the shared cache.
  4. For the next hour, every request the real victim agent makes is refused without any outbound fetch being attempted, because hit.failed short-circuits at :357. If the victim was mid-mint, it cannot mint.

Demonstrated. Two verifyRequest calls through a real makeLookup with a failing fetch: the first made one outbound attempt, the second made none, and the cache held {"failed":true,...} for the victim's URL.

What to do. Give failures a much shorter TTL than successes -- 30 to 60 seconds is enough to stop the prober amplification the comment is worried about -- and cap consecutive remembered failures rather than pinning them for an hour. An hour is the right number for a positive cache (it is the deliberate revocation window, and the comment at :351-354 says so); it is the wrong number for a negative one.

13.4 The door makes outbound HTTPS requests to an attacker-chosen host before any signature is verified, and does not de-duplicate them

Severity: Medium

warden/src/door/verify.mjs:104 and :129 (the lookup runs inside the verifier callback, before verifier() at :143), warden/src/door/directory.mjs:363-369 (the cache is written only after the fetch resolves, so there is no in-flight map).

The lookup must happen before verification -- you cannot check a signature without the key -- so the trigger itself is not a defect. What follows from it is: an unauthenticated caller with a syntactically well-formed but cryptographically worthless Signature-Input gets the Warden to open an HTTPS connection to any publicly routable host it names, and there is no per-IP rate limit anywhere in the stack (see 13.2 on the nginx template).

Failure scenario, in order:

  1. The attacker sends N concurrent requests to POST /mcp, each carrying Signature-Agent: "https://target.example", a well-formed Signature-Input naming the five required components, and Signature: sig1=:AAAA:.
  2. Each request reaches lookupKey before any cryptography runs. Because the cache is written only when a fetch settles, all N requests miss and all N issue their own outbound GET https://target.example/.well-known/http-message-signatures-directory.
  3. Each outbound connection is held for up to FETCH_TIMEOUT_MS (3 s, directory.mjs:15) and may buffer up to 64 KB (:14). N is bounded only by how fast the attacker can send.
  4. The attacker gets a request reflector aimed at a third party, and the Warden gets N concurrent sockets plus up to 64 KB each of resident memory, from requests that never had a valid signature.

Demonstrated in part. A request with Signature: sig1=:AAAA: and no valid key triggered the lookup with the attacker's chosen agent value ("https://attacker-chosen.example") and only then refused. The absence of in-flight de-duplication is read from the code, not measured under load.

The destination is constrained, and well: HTTPS only, port 443 only, no credentials, no redirects followed, path fixed to /.well-known/http-message-signatures-directory with no query, method GET, and every resolved address checked inside the socket's own lookup so there is no check-then-connect window. That is a much better guard than most. It does not bound the number of requests, which is the gap here.

What to do. Keep an in-flight Map keyed on the same URL as the result cache, so concurrent lookups of one URL share one fetch. Cap concurrent outbound directory fetches process-wide (a small semaphore; refuse with directory when full). Both are small and neither weakens the address guard.

13.5 reason: "directory" is unreachable through the real lookup, so a directory outage tells an honest client its key is unknown

Severity: Medium

warden/src/door/verify.mjs:128-140 and warden/src/door/directory.mjs:363-368.

verifyRequest distinguishes the two cases deliberately, and the comment at verify.mjs:131-134 states the intent exactly: "The directory could not be reached. Fail CLOSED, but say so: telling an honest client its crypto is bad during an outage sends it to debug the wrong thing." That branch only fires if lookupKey throws. The real makeLookup does not throw on a fetch failure -- it catches, remembers the failure, and returns null (directory.mjs:365-367). null falls to the next branch and sets reason = "unknown-key".

Failure scenario, in order:

  1. An agent's own JWKS host has a transient outage, or the agent is the target of 13.3.
  2. The agent's next request is refused with {"reason":"unknown-key"}.
  3. The protocol doc's table says unknown-key means "we could not find that key id", and says directory means "your directory could not be fetched. Ours, not yours: try again" (docs/2026-09-01-mro-raw-protocol.md, section 1). The agent, reading its own documentation correctly, concludes its key id is wrong and goes to re-derive its RFC 7638 thumbprint -- the one thing the doc already warns is the trap that "produces a wrong key id silently".
  4. It re-registers, or gives up. Neither fixes anything, and the failure is cached for an hour regardless.

Demonstrated. Two verifyRequest calls through a real makeLookup whose fetch throws both returned {"ok":false,"reason":"unknown-key"}. The only way to reach reason: "directory" through the real lookup is a fetched JWKS containing an entry that makes jwkToKeyID throw inside the loop at directory.mjs:372-375, which is not the case the branch was written for.

What to do. Have makeLookup distinguish "fetched, and the key is not in it" (return null) from "could not fetch" (throw, or return a sentinel the caller maps to directory). Then the branch and the documented table both become true.

13.6 Two ranges are missing from isBlockedAddress

Severity: Low

warden/src/door/directory.mjs:61-74 (blockedV4) and :95-138 (isBlockedAddress).

Measured against the guard directly: 192.88.99.1 (6to4 relay anycast, RFC 7526) and 2001::1 (the Teredo prefix 2001::/32) are both allowed; so is 2001:db8::1 (documentation). Everything else probed is blocked correctly, including all the forms this project has been bitten by before: ::ffff:127.0.0.1, ::ffff:0:127.0.0.1, 64:ff9b::7f00:1, 2002:7f00:1::1, fe80::1, fd00::1, 127.1, 192.0.0.1, 240.0.0.1, 255.255.255.255. Decimal, hex and octal IPv4 literals are handled because the WHATWG URL parser normalises them before the guard sees them -- https://2130706433/, https://0x7f.0.0.1/ and https://0177.0.0.1/ all arrive as hostname 127.0.0.1 and are refused with "directory resolves to a blocked address".

Failure scenario: on a host with a 6to4 or Teredo tunnel configured, a directory URL resolving to 192.88.99.1 or into 2001::/32 reaches an encapsulation relay rather than the public internet. On this VPS neither tunnel exists, so this is hardening, not a live path -- said plainly because the guard elsewhere in this file is genuinely strong and this should not be read as undermining it.

What to do. Add a === 192 && b === 88 && c === 99 to blockedV4 (it needs the third octet, so pass it through), and bytes[0] === 0x20 && bytes[1] === 0x01 && bytes[2] === 0x00 && bytes[3] === 0x00 for Teredo. 2001:db8::/32 is harmless and can be left.

13.7 The spent-nonce set is shared between two protocols and is written before the proof verifies

Severity: Low

warden/src/server.mjs:88 (one seen Set), :171 (GET /keys/nonce mints from the same secret and the same issueChallenge), :213-218 (the registration checkNonce callback adds to seen before registerRoute verifies anything), warden/src/door/middleware.mjs:107-111 (sweepSeen).

Three small things, none of them a bypass:

  1. A door challenge and a /keys/nonce nonce are the same string format under the same HMAC key, and they burn into the same Set. Either can be spent as the other. Nothing is gained by doing so -- the entry answer is a public function of public inputs, and the registration proof needs the private key -- but it means anyone holding a nonce string can burn it for the other protocol, and the two mechanisms cannot be given different sweep windows later without separating the sets first.
  2. checkNonce at server.mjs:216-217 adds the nonce to seen before the Ed25519 proof is checked. That is the correct order for anti-replay (the nonce must be spent whether or not the proof passes), but it means an unauthenticated caller can insert one Set entry per request. Bounded by the sweep at 10 seconds' traffic, so it is a small memory cost rather than an unbounded one.
  3. sweepSeen(seen, issuedAt = new Map(), now) never reads issuedAt (middleware.mjs:107-111) -- the timestamp is recovered from the challenge string itself. The parameter is dead and server.mjs:92 does not pass it.

What to do. Nothing urgent. If the two nonce kinds ever need different lifetimes, separate the sets first. Drop the dead parameter.

13.8 The protocol document's own worked example would be refused by the current door, and "exactly these components" is enforced as "at least"

Severity: Low

docs/2026-09-01-mro-raw-protocol.md, section 3 (the "real set" of headers), against warden/src/door/verify.mjs:45 and :115-120.

Two disagreements between the captured-on-the-wire document and the code:

  1. The worked example prints Signature-Input: sig1=("@authority" "@method" "@path" "signature-agent");... with no content-digest, and no content-digest header in the set above it. Three paragraphs later the same section says content-digest "is not optional". The example predates the 2026-09-02 change and would now be refused with reason: "components". The document's whole premise is that nothing in it is written from memory and a reader can run warden/tools/protocol-transcript.mjs and compare; a reader who copies the example gets a refusal.
  2. The document says "The signature must cover exactly these components". The code checks a subset relation (covered.includes(component) for each of the five), so a superset is accepted.

Demonstrated for (2). A signature over ["@authority", "@method", "@path", "signature-agent", "content-digest", "@authority", "@query"] -- one duplicate and one extra -- was admitted. This is not a weakness: http-message-sig builds the signature base itself from the request (node_modules/http-message-sig/dist/index.mjs:120-129) rather than trusting a caller-supplied base, component parameters are ignored for value extraction, and a ;req parameter on a raw request message throws (:97-103), so extra components only ever bind more. But the document states a stricter rule than the code enforces, and a client author who reads "exactly" will build a client that is more brittle than it needs to be.

What to do. Regenerate the section 3 example from a current capture. Change "exactly these components" to "at least these components".

13.9 The fetched JWKS is not validated, but the library narrows it -- and the accepted algorithm set is wider than every document says

Severity: Info

warden/src/door/directory.mjs:372-375 (no kty, crv, alg or size check before use), warden/node_modules/web-bot-auth/dist/chunk-VXDWK3MV.mjs (verifierFromJWK).

makeLookup hands whatever the third-party directory returned straight to verifierFromJWK. Read from the installed source rather than assumed: verifierFromJWK accepts exactly two shapes and throws on everything else -- kty: "OKP" with crv: "Ed25519", and kty: "RSA" with alg: "PS512" (RSA-PSS with SHA-512). A symmetric oct key is refused, so the obvious "hostile directory publishes a key it also holds the private half of" is not available, and in any case the key id is the thumbprint of that same JWK, so an attacker doing it is only authenticating as an identity it invented.

The RSA branch is the undocumented part. The spec, llms.txt and the protocol doc all say Ed25519, and POST /keys enforces Ed25519 at directory.mjs:423, but a third-party directory may present an RSA key and it will be used. Measured for cost, because an unbounded modulus inside a 64 KB directory looked like a CPU lever: a matching-length verify took 0.7 ms at 2048 bits, 2.5 ms at 16384, 0.7 ms at 65536 and 1.2 ms at 98304 (the largest a signature can be inside Node's 16 KB header limit). It is not a lever. Reported as an accepted-surface note, not a defect.

The one real cost is the thumbprint loop at :372-375: a 64 KB directory holds roughly 600 minimal JWKs and each costs one crypto.subtle.digest. It runs once per URL per hour because of the cache, so it is not a lever either.

What to do. Decide whether RSA-PS512 is in the protocol. If it is, say so in the spec and the protocol doc. If it is not, refuse anything but {kty: "OKP", crv: "Ed25519"} in makeLookup before calling verifierFromJWK, which also removes the modulus question permanently.

13.10 There is no admitted-for-the-day cache, and no per-key lockout: the code is stronger than the spec on one and weaker on the other

Severity: Info

docs/specs/2026-08-27-machine-readable-only-design.md:282 and :293-294, against warden/src/door/middleware.mjs:59-93 and warden/src/server.mjs:245-247.

Recorded precisely, because the brief asks for exactly what is cached:

  • The spec says "the key id is admitted for the rest of the UTC day (in-memory set, cleared at 00:00 UTC)". No such set exists. Every request through the door runs the full sequence every time: pin the URL, parse the signature, check the five components, check the five-minute window, look the key up, verify the signature cryptographically, compare the content digest against the body just read, then check and burn the challenge. There is no session, no cookie, and no admitted-key state of any kind. The code is materially stronger than the document it was built from, and the document should be corrected rather than the code.

  • The only per-request cache in the door path is the third-party directory cache (directory.mjs:324, one hour, 256 entries, keyed on URL), which caches keys, not admissions. A cached key still has to verify a signature.

  • The spec at :294 also says "a key that fails ten in a row is paused for an hour". Not implemented. There is no failure counter anywhere in warden/src/. Combined with the absence of any limit_req in the nginx template (13.2), an attacker gets unlimited signature attempts. That costs nothing today because forging an Ed25519 signature is not a guessing game, so this is an Info rather than a Medium; it matters because the document is claiming a control that a reader would count on.

  • The same sentence (:293-294) says the challenge is "bound to the signed request's nonce". It is not. The challenge and the RFC 9421 nonce are two independent values that never meet: checkChallenge (warden/src/door/challenge.mjs:73-87) never sees params.nonce, and params.nonce is passed through by the library and dropped (warden/node_modules/web-bot-auth/dist/index.mjs:113). Binding them, as the spec already describes, is one of the two fixes offered for 13.1. (Verifier: citation corrected from :104 to :113.)

13.11 The unauthenticated routes, and what they expose

Severity: Info

warden/src/server.mjs:118-173. Six route families answer before the door:

GET / and GET /llms.txt the door page and the instructions static text
GET /client.mjs, GET /skill.md documented as 404 nothing

/t/{id} was probed against a live server: /t/1, /t/0, /t/-1, /t/1e3, /t/99999999999999999999999 and a 400-digit id all returned a clean 404 {"ok":false,"reason":"unknown-token"}. 13.12 Verified negatives on the challenge primitive and the digest

Severity: Info

Each of these was specifically looked for and is correct, so that a later reader does not re-audit them:

  • The HMAC comparison is constant time. challenge.mjs:15-20 decodes both hex strings to Buffers, refuses on a length mismatch or a zero length, and uses timingSafeEqual. Non-hex input decodes short and fails the length check. The same function guards the challenge answer at :84.
  • nonce || timestamp is unambiguous. The MAC input is ${nonce}.${ts} (:22-23) and verifyNonceMinted requires the challenge to split into exactly three dot-separated parts (:51-52), so neither the nonce nor the timestamp can contain a dot in any accepted challenge. "A.B" therefore determines A and B uniquely; there is no second (nonce, ts) pair with the same MAC input.
  • The timestamp is bounded on both sides, and it is checked after the HMAC: !Number.isFinite(issuedAt) || now - issuedAt > CHALLENGE_MS || now < issuedAt (:59-62). A far-future timestamp with a valid HMAC is refused by now < issuedAt, so there is no forever-valid challenge. The order is also right -- an attacker cannot get an unauthenticated timestamp judged.
  • The nonce is 256 bits from a CSPRNG: randomBytes(32) at :33.
  • @authority is pinned to the configured domain, never to Host. pinnedUrl (middleware.mjs:34-38) reduces the request target to pathname + search and rebuilds it on https://${domain}, and http-message-sig's getUrl uses the Host header only when the message carries a protocol property (node_modules/http-message-sig/dist/index.mjs:35-39), which toRequestLike does not set. So the library takes the pinned absolute URL. The protocol doc's claim is accurate. server.mjs:110 dispatches on the same reduction, so the routed path and the signed path cannot come apart.
  • The digest is over the exact bytes the handler parses. server.mjs:238 reads the body once into raw; middleware.mjs:80 compares contentDigest(raw) to the header; mcp/server.mjs:131 replays Buffer.from(raw, "utf8") to the MCP adapter. Same bytes, same encoding, one read. There is no path where the body is parsed before the digest check on a door-gated route (POST /keys parses before any door check, but it is outside the door by design and has its own proof). One consequence worth knowing: a body that is not valid UTF-8 is mangled by Buffer.concat(chunks).toString("utf8") at server.mjs:56 and will never match its own digest, so such a request can never be admitted. That fails closed.
  • The verified key id comes from the cryptography, not from a header. verify.mjs:148 captures params.keyid inside the verifier callback after verifier() returned, and admit carries that value forward; nothing re-reads the header afterwards. Pinned at verify.test.mjs:253.
  • Multiple signatures are impossible. parseSfvDictionary throws on a Signature-Input dictionary with more than one member (node_modules/http-message-sig/dist/index.mjs:249-251), so there is no "one good signature among several" confusion to exploit, and coveredComponents' use of lastIndexOf is belt and braces.

Two supporting details that make the trace hold. web-bot-auth's verify throws rather than returning false on every failure it detects -- wrong tag, created in the future, expires past, missing keyid (node_modules/web-bot-auth/dist/index.mjs:94-107) -- and a missing or non-numeric created becomes a TypeError on params.created.getTime(), which is also a throw. And server.mjs:254 is return await, not a bare return, so a rejecting MCP handler becomes the 500 rather than an unhandled rejection that takes the process down.

The one thing that is not a catch but behaves like one: an absent header is read as "" by http-message-sig's extractHeader (node_modules/http-message-sig/dist/index.mjs:22-33) rather than as an error. A signature can therefore cover signature-agent while sending no such header, and the base line is "signature-agent": . That is safe here, and is in fact the mechanism the local-mirror path uses (makeLookup treats a null agent as ours, directory.mjs:332), but it is worth knowing that "the signature covers X" does not imply "X was sent".

The trust boundary at a glance

Bound by the signature, and therefore not tamperable on an otherwise valid request: the HTTP method (uppercased); the request path, after it has been reduced to pathname on this service's own origin; the authority, which is always the configured MRO_DOMAIN and never the Host header; the Signature-Agent header value (with runs of whitespace collapsed to single spaces by the library); the Content-Digest header value and, through it, the exact body bytes the MCP handler will parse; and inside @signature-params the created, expires, keyid, alg, tag and nonce parameters.

Not bound, and therefore attacker-controlled on an otherwise valid request: the challenge and challenge-response headers -- which is what makes 13.1 work, since a fresh challenge can be fetched and answered by anyone holding the key id; the query string, because @path yields only pathname and @query is not required (no consumer in this service reads it today, but the router and the digest both ignore it); Host, Content-Type, Accept, Content-Length, and every X-Forwarded-* header nginx adds; the source address; and the identity of whoever actually transmits the bytes. Above all, the fact that this signature has been presented before is not recorded anywhere, so within expires the signature authenticates the request rather than the presentation of it.

The good news first, because it is real. The cancelSettlementOnRefusal fix (x402.mjs:108-118) holds on every return point inside both paid handlers, not only the one it was measured on. Every refusal a paid handler can produce carries ok: false, so every one of them is converted to a complete MCP result with isError: true; mcp/server.mjs:104 then passes it through by shape rather than re-wrapping it. What is wrong is one level down. The money question this service has been asking is "can a refusal charge?". The question it has not asked is the mirror image: can a success fail to charge? It can, it is not detectable after the fact, and nothing in the codebase records that a payment ever settled.

14.1 The paid effect is committed before settlement, and the settlement result is never read

Severity: Critical

warden/src/mcp/tools/mint.mjs:95-99 and warden/src/mcp/tools/upgrade.mjs:194 (the writes), against @x402/mcp/dist/esm/index.mjs:940-1001 (when settlement happens).

The authorization flow settles AFTER the handler returns. That is the whole premise of the cancelSettlementOnRefusal fix and it is correct. But it cuts both ways, and only one way was followed. Reading @x402/mcp:940-1001 in order:

940  let result;
941  try { result = await handler(args, context); }        <- our rows are written HERE
...
971  if (result.isError) { ...cancel... }
989  return settlePaymentResult(...)                       <- the money moves HERE
...
1054 if (!settleResult.success) {
1055   return createSettlementFailedResult(...)            <- and if it does NOT move
1062 }

createSettlementFailedResult returns an error to the agent. It does not, and cannot, undo anything the handler did. And what the handler did is the whole product: mint.mjs:95-99 inserts the mints and tokens rows inside a transaction, and upgrade.mjs:194 inserts the mark_orders row. Those rows are the mirror, the mirror is what the Clock reads, and the Clock writes them on chain at 00:05 UTC without ever asking whether the payment landed. Grepping src/ for paymentTx returns nothing: the columns exist in schema.sql:48 and :72 and no code in the service ever writes them. There is no onAfterSettlement hook, no settle-response inspection, and no reconciliation of revenue against tokens.

Failure scenario, no attacker required. An agent mints. Verification passes. The handler writes both rows and returns { ok: true, tokenId: 3, ... }. settlePayment is then attempted and fails -- the facilitator errors, the RPC times out, the payer's balance moved, the authorisation expired. The agent is handed a "Payment settlement failed" result and keeps its dollar. Token 3 is minted on chain that night anyway. Nobody is told, no alert fires (the alert calls at mint.mjs:60, :70, :82 and :103 are all on refusal paths, and this is the success path), and the only trace is a row with a NULL paymentTx that looks exactly like every paid row.

Failure scenario, with an attacker, and it is cheap and repeatable. USDC on Base implements EIP-3009 in full, including cancelAuthorization(authorizer, nonce). So:

  1. Agent calls mint with a correctly signed authorisation from a funded wallet.
  2. verifyPayment runs before the handler and passes: the nonce is unused, the balance is there, the signature is good.
  3. While the handler is doing its four to thirty-six eth_call round trips (paidWriteBlock at mint.mjs:68, then chain.freeIdFrom at :80, which probes up to 32 ids at a 3-second timeout each, read.mjs:176-183), the attacker submits cancelAuthorization for that same nonce on Base. Blocks are two seconds.
  4. The handler writes the rows and returns ok: true with a token id.
  5. settlePayment broadcasts transferWithAuthorization, which now reverts on a cancelled nonce. Settlement fails.
  6. The attacker has a token. It paid nothing. It also knows immediately whether it won, because the result tells it, so a loss simply costs the normal $1 and the attempt can be repeated until it wins.

The same applies to upgrade, where the prize is up to $1,250.00 for a Vessel. A cheaper deterministic variant exists: @x402/evm:599 only requires validBefore >= now + 6, so an authorisation signed with seven seconds of life passes verification and is guaranteed to be dead by the time a handler that made a dozen RPC calls returns.

What to do. The effect must not be committed until settlement is confirmed. Concretely: move the mirror write out of the x402 handler and behind the settlement result. @x402/mcp gives a place to do it -- config.hooks. onAfterSettlement (index.mjs:1063-1069) fires only after settleResult.success -- so the handler can reserve provisionally and the hook can commit, with the reservation expiring if the hook never fires. At minimum, record the settlement receipt into mints.paymentTx / mark_orders.paymentTx from that hook and make the Clock refuse to write a row that has none, so an unsettled effect is a row the Clock skips rather than a token it mints. That also gives the reconciliation this service currently cannot perform at all.

14.2 One authorisation is bound to an amount, and to nothing else

Severity: High

warden/src/pay/x402.mjs:182-187 (what the demand contains), against @x402/core/dist/esm/chunk-H7ETXA5T.mjs:1056-1077 (what buildPaymentRequirements produces) and :2007-2020 (what a submitted payload is matched against).

wrapperFor builds the demand from { scheme, payTo, price, network }. The requirement object that comes back holds scheme, network, amount, asset, payTo, maxTimeoutSeconds and extra -- and nothing else. The resource identity (mcp://tool/mint, the description naming the Mark and the token) is a SIBLING of accepts in the payment-required response (chunk-H7ETXA5T.mjs:1124-1129), not a field inside it, and paymentRequirementsMatchAccepted deep-equals only the requirement. The EIP-3009 authorisation the agent signs covers from, to, value, validAfter, validBefore and nonce -- also no resource.

Two consequences, one benign and one not.

Cross-tool substitution at equal price is possible and undetectable. mint costs $1.00 and Hush costs $1.00; the bought Iris costs $25.00 and Aura costs $25.00. The demands for each pair are byte-identical, so a payload obtained for one is accepted for the other. On its own this gains an agent nothing (one nonce still settles once), but it means an x402 receipt cannot be attributed to a tool, a token, a Mark id or a variant, and combined with 14.1 there is no way to audit what was paid for what.

Nothing dedupes an authorisation across concurrent calls. The resource server is stateless with respect to nonces; the only single-use enforcement is the chain's authorizationState, which is not consulted until settlement. Failure scenario: an attacker registers keys K1 and K2 through POST /keys (the limiter at bootstrap.mjs:58-73 is per-thumbprint, so a fresh keypair resets it), then fires mint from both at once carrying the SAME signed $1 payload. Both verify -- the nonce is unused at that instant. Both handlers run. Because the mirror's nextTokenId is MAX(tokenId)+1 (queries.mjs:120), a truly simultaneous pair collide on the mints primary key and the loser refuses cleanly, so the attacker staggers them by polling /t/<id> until the first row appears (it appears before the response returns, and well before settlement). Both settle; one wins the nonce, the other fails and is discarded per 14.1. Two tokens, one dollar. upgrade has no shared id to collide on at all -- two different Marks on two different tokens race cleanly.

What to do. 14.1's fix removes the payoff, because a failed settlement would no longer leave an effect. Independently, record every accepted settlement's nonce and refuse a second use of it, and put the tool, token, Mark id and variant into the demand's extra so the receipt says what was bought.

14.3 "Bound to the caller" is decided from the mirror, which lags an on-chain rebind by up to a day

Severity: High

warden/src/mcp/tools/upgrade.mjs:44 and :186, warden/src/mcp/tools/seed.mjs:30, against warden/src/mcp/tools/checkin.mjs:31-43 and warden/src/clock/reconcile.mjs:101-108.

14.7 The gateway's own two refusals carry no isError

Severity: Low

14.8 TREASURY_ADDRESS is regex-validated only

Severity: Low

14.10 The price strings and amounts are correct end to end

Severity: Info

15.1 The key-generation script hands the private key to cast as a command-line argument, and the comment two lines above says it does not

Severity: High

scripts/make-clock-key.sh:39-43.

  # Read the key into a variable and hand it to cast on stdin. It is never
  # echoed, and never becomes a command-line argument (which would be visible
  # to anyone running `ps` while this runs).
  CLOCK_KEY="$(grep '^CLOCK_PRIVATE_KEY=' "$ENV_FILE" | head -1 | cut -d= -f2-)"
  cast wallet address --private-key "$CLOCK_KEY"

The comment describes stdin. The code does not use stdin. "$CLOCK_KEY" is expanded by the shell before execve, so the literal 66-character private key is cast's argv[3].

That matters more than the usual "visible to ps" phrasing suggests. On Linux /proc/<pid>/environ is mode 0400 and readable only by the process owner, but /proc/<pid>/cmdline is mode 0444 and readable by every local user, regardless of uid. So the argument is not protected by the same boundary the 0600 .env file is protected by. It is the only place in this repository where the Clock's key crosses out of a file the owner alone can read.

Failure scenario. The operator re-runs make-clock-key.sh to remind themselves of the Clock's address -- which is exactly what lines 36-44 exist for, and the script's own header advertises it as "safe to run again". Any other local account on the box, or any service running under a different uid (nginx worker, a container sharing the host PID namespace, a compromised dependency in an unrelated project on this VPS), polling cat /proc/*/cmdline in a loop reads the key out of cast's argv. It then has the only signing key in the piece; see the blast-radius subsection below for what that buys. The window is one cast invocation, but the poll is cheap and the script is designed to be run repeatedly.

This is the one finding in this section that discloses the key rather than merely widening its reach. It is a real primitive, not a theoretical one, but I have not demonstrated the race -- I did not run a watcher against a live invocation, because doing so would have put a key in a transcript.

What to do. Stop reading the key back at all. The address is public and is already printed once at generation time (line 74). Write it into the env file as a CLOCK_ADDRESS= line at generation, and have the re-run branch at :36-44 echo that instead of deriving it from the secret. Nothing then needs to touch the key to answer "which address is this", and the comment at :39-41 becomes true by construction rather than by hope. If the derivation must stay, it has to go through stdin or a file descriptor -- an exported variable is no better, since the expansion still lands in argv.

15.2 A check-in batch that lands on chain but is never marked written wedges every future night, permanently

Severity: High

warden/src/clock/write.mjs:159, warden/src/clock/run.mjs:169-172, warden/src/clock/batch.mjs:74 and :80-83, warden/src/clock/reconcile.mjs:69-71.

Three facts combine into a trap.

  1. The receipt wait is uncaught. write.mjs:159 is const receipt = await pub.waitForTransactionReceipt({ hash }); with no try. Every other network call in send() is wrapped; this one is not. A transport error, a WaitForTransactionReceiptTimeoutError, or the systemd unit's TimeoutStartSec=600 firing all leave the transaction in the mempool and abandon the run.
  2. The mirror write happens after the receipt. run.mjs:169-172 marks the entries written only once writeCheckInChunk returns. Anything that throws between the transaction landing and that loop completing -- including the SQLITE_BUSY of finding 15.4 -- leaves the rows queued while the chain has them.
  3. Nothing ever heals that. run.mjs:170 is the only caller of markCreditWritten anywhere in src/ (checked by grep across the tree), and reconcile deliberately ignores BatchCheckedIn -- reconcile.mjs:70's applied map lists only Rested, Transfer, Rebound, Minted and MarkApplied, and warden/test/clock-reconcile.test.mjs:141-149 pins that as intended behaviour. There is no path by which a credit row learns it is already on chain.

Now the trap. Those stale rows are re-offered by q.pendingCredits on the next run. The contract reverts DayNotAdvanced(id) on each, one id per revert. batch.mjs:123-135 drops exactly one id per attempt, and maxAttempts is 12 (batch.mjs:74). At attempts >= maxAttempts the function returns { written: [], dropped: [...all remaining as "attempts-exhausted"] } (:80-83) -- and dropped rows are never marked written, so they stay queued too.

Failure scenario, in order.

  1. Night 1: 400 agents check in. The Clock sends one batchCheckIn covering 400 entries. It mines. The public RPC drops the connection during waitForTransactionReceipt. The run dies at main.mjs:106 with exit 1. All 400 credit rows are still queued; all 400 days are on chain.
  2. Night 2: pendingCredits returns those 400 plus the new day's. Attempt 1 simulates and reverts DayNotAdvanced(<first stale id>). That one id is dropped. Attempts 2 through 12 drop eleven more. Attempt 12 exhausts. written is empty. Nothing is credited. The 389 remaining stale rows and every fresh row stay queued.
  3. Night 3, and every night after: identical. The queue only grows.

Check-ins stop landing on chain permanently, from one dropped TCP connection, with no alert that says so -- summary.dropped is logged per entry at run.mjs:176 as "was refused ... and stays queued", which reads like the normal poison-row path, and the exit code is 0 because aborted is null and stuck is empty. The days are the artwork; a day that never lands is not recoverable later, because batchCheckIn refuses day <= s.lastDay and, once the token does advance, the missed day can never be backfilled.

The existing suite does not cover this. warden/test/clock-batch.test.mjs:82-93 proves three poison entries are dropped one at a time and the good ones land; nothing tests twelve or more, and nothing tests the "written on chain, queued in the mirror" state at all.

What to do. Two changes, either of which breaks the loop, and both are worth making.

  • Wrap waitForTransactionReceipt in write.mjs:159 the way every other call in send() is wrapped, and return a distinct { ok: false, reason: "receipt-unknown", hash }. A hash whose fate is unknown is a different thing from a send that failed, and the caller must be told so rather than have the run die.
  • Make DayNotAdvanced self-healing rather than a drop. The contract already told the Clock the truth: that token's lastDay is at or past this day, so the credit is on chain. Call markCreditWritten for it instead of dropped.push. That converts the wedge into automatic recovery and removes the only unbounded consumer of maxAttempts. NoSuchToken and Resting should stay drops; DayNotAdvanced is the one entry error that means "already done".

15.3 The spec's "only with a paid settlement" is false: a stolen Clock key mints for free, and the damage it does is permanent and unrecoverable

Severity: High

warden/src/clock/main.mjs:31 (the key), and contracts/src/MachineReadableOnly.sol:241-272 (mint), :294-341 (batchCheckIn), :480-528 (applyMark), :598-645 (seed).

The spec claim under test is: "an attacker can mint (only with a paid settlement) and check in, but cannot move tokens or funds."

The second half holds. I enumerated every onlyWarden function. There are four: mint, batchCheckIn, applyMark, seed. None takes or moves value. The Warden address is not the owner (setWarden, setRenderer, setSupplyCap, setWalletCap, pause, sunset, setUpgrade are all onlyOwner), it is not an ERC-721 operator for any token, and the contract holds no ETH or ERC-20 balance and has no receive. checkInWithVoucher verifies a Warden EIP-712 signature but vouchersEnabled ships false. So: no transfers, no funds, no renderer swap, no sunset. Confirmed.

The parenthetical does not hold. The 1 USDC price is a Warden constant, not an on-chain value -- CLAUDE.md states this explicitly, and mint at :241 has no payment argument, no msg.value check, and no settlement proof. A stolen key calls mint(id, to, keyId, code) directly and pays nothing but gas.

What that actually costs, in order.

  1. Permanent supply destruction. supplyCap is 10,000 and walletCap is 20 (constructor, :126-127). totalMinted only ever increments (:266), there is no burn anywhere in the contract (grepped: no _burn, no burn), and setSupplyCap can raise the cap but cannot un-mint. An attacker spreads mints across 500 addresses of their own and mints out the entire collection in an afternoon, at Base gas prices. The piece is then over, permanently, and the owner has no remedy short of deploying a different contract -- which Hard Rule 1 forbids.
  2. Permanent per-key mint burn. _hasMinted[keyId] = true is set at :265 and the comment at :238 records that it is never freed, not even by rebind. The Warden's key directory is public by design -- it publishes every registered agent's JWK, and keyId is the RFC 7638 thumbprint of that JWK, so every registered keyId is computable by anyone. The attacker enumerates the directory and mints one token against each key, to their own address. Every agent that had registered can now never mint, forever, and the token bearing their key is owned by the attacker.
  3. Permanent artwork corruption. batchCheckIn lets the Warden credit any day in (lastDay, today()] for any token. level and streak are the artwork. The attacker backfills every token to today in one transaction: levels jump, streaks are rewritten, and neither can ever be reduced. This is the same surface section 12.3 raised as a forging concern; a stolen key is the version of it that needs no cooperation from the operator.
  4. Permanent Mark closure. applyMark writes _marks[id] with no clearing path (:520-524), and every exclusion is permanent by design. The attacker applies the free earned Marks to every token that qualifies, closing the bought side of each pair forever. Tokens lose Marks they could have bought; nobody gets a refund because nobody paid.

The one thing the FutureDay bound genuinely prevents. batchCheckIn:319 rejects day > today(), so lastDay can never be pushed into the future and no token can be permanently bricked against future check-ins. That bound -- one of the seven pre-mainnet fixes -- is what stops this from being total. It holds; I read it and it is unconditional.

What to do. The right framing for the launch documents is not "an attacker can only mint and check in". It is: a stolen Clock key cannot take money or tokens, but can end the piece. Two concrete mitigations, in order of value:

  • Lower supplyCap to something near actual demand and raise it deliberately as the collection fills. A cap of 10,000 set on day one is 10,000 free mints sitting behind one key. This is an onlyOwner call, needs no redeploy, and costs nothing.
  • Give the operator a rehearsed rotation: setWarden(newAddress) is a single owner call and instantly revokes the old key (onlyWarden reads warden live). Write it into the runbook with the exact command, because the response window here is minutes.

15.4 Two processes write the same SQLite file with a busy timeout of zero

Severity: Medium

warden/src/mirror/db.mjs:16.

const db = new DatabaseSync(path);

No options object. Per the live node:sqlite documentation (https://nodejs.org/api/sqlite.html, fetched 2026-09-04), DatabaseSync's timeout option is the SQLite busy timeout and its default is 0. With WAL enabled (db.mjs:17) readers do not block writers, but two writers still serialise on a single write lock, and with a zero busy timeout the loser gets SQLITE_ERROR: database is locked immediately rather than waiting.

Both processes open this file for writing. warden/ecosystem.config.cjs:32 runs the Warden with --env-file=.env from warden/, and warden/deploy/mro-clock.service:16 runs the Clock from the same directory against the same STATE_DB_PATH. The Clock fires at 00:05 UTC plus up to 60 seconds of RandomizedDelaySec while the Warden is serving agents.

Failure scenario. An agent's checkin opens its transact() write (queries.mjs:256-266) at 00:05:31. The Clock, mid-way through run.mjs:169-172, calls markCreditWritten and gets database is locked straight back. That throw is uncaught: it leaves runClock, reaches main.mjs:105, and the run exits 1 -- after the batch has landed on chain. That is precisely the poisoned state finding 15.2 turns into a permanent wedge. This is the most likely way 15.2 actually happens in production, and it needs no network fault at all.

The reverse direction is milder: the agent's transact rolls back and the check-in returns an error, which the agent can retry.

There is a second, smaller defect in the same place. transact at :257 runs db.exec("BEGIN") outside the try. If BEGIN itself is the statement that gets SQLITE_BUSY, the catch still runs db.exec("ROLLBACK"), which throws cannot rollback - no transaction is active and replaces the informative error with a misleading one.

Verifier: the second sub-defect is REFUTED; the main claim is confirmed and probed. SQLite's BEGIN is DEFERRED by default and takes no lock, so it cannot get SQLITE_BUSY. Probed on the installed Node 24.14.1: BEGIN succeeded against a database another connection held write-locked, the subsequent INSERT threw, and the catch's ROLLBACK then worked correctly. The misleading-rollback path is unreachable as described. The main claim holds and was measured: the default new DatabaseSync(path) threw database is locked after 1 ms, while { timeout: 5000 } waited 5,025 ms, and https://nodejs.org/api/sqlite.html (fetched live) gives the default as 0.

What to do. new DatabaseSync(path, { timeout: 5000 }). Five seconds is far longer than any write here takes and turns a hard failure into a wait. Then move BEGIN inside the try so a failed BEGIN reports itself.

15.6 Reconcile reads to the chain head with no confirmation depth, and applies one-way state from it

Severity: Medium

warden/src/clock/run.mjs:301 (const head = await publicClient.getBlockNumber()), warden/src/clock/reconcile.mjs:86-89 (Rested), :110-112 (Minted), warden/src/mirror/queries.mjs:101-103.

The window is lastReconciledBlock + 1 .. head, and head is the unsafe head -- there is no subtraction of a confirmation depth anywhere. The cursor is then advanced past it (main.mjs:85), and those blocks are never re-read.

Two of the five handled events write state that has no reverse.

  • Rested calls q.setResting(tokenId), and queries.mjs:101-103 documents that there is deliberately no way to clear it.
  • Minted calls q.markMintWritten(tokenId), which moves both the mint row and the token row to written. A written mint is never offered by pendingMints again.

Failure scenario. A Base sequencer reorg drops a block containing a Minted event that reconcile has already read. The mirror now says that paid mint is written; the chain has no such token. pendingMints will never return it, the Clock will never re-send it, stuckMints will not report it (it filters solveState = 'failed', and this one solved fine), and the agent who paid 1 USDC has nothing. Nothing in the service ever compares the mirror's written mints against ownerOf. The equivalent Rested case seals a token in the mirror that is not sealed on chain, which the ladder tool (warden/src/mcp/tools/ladder.mjs:66,144) and tokenView report to agents; the paid gates read the chain (warden/src/mcp/gates.mjs:43), so that half is display and advice rather than money.

I am flagging this as theoretical rather than demonstrated: I did not observe a Base reorg, and Base's sequencer makes deep reorgs unlikely. The point is that the code has no depth parameter at all, so its resilience is zero rather than small, and the state it writes on a wrong read is one-way by design.

What to do. Read to head - N rather than head, with N small (Base blocks are 2 seconds; N = 30 costs a minute of freshness on a job that runs daily). That is a one-line change at run.mjs:301 and it costs nothing here, because this reconcile has no latency requirement whatsoever.

15.7 A chunk too big to estimate aborts the whole run instead of halving, and the chunk size rests on an explicitly unverified number

Severity: Medium

warden/src/clock/write.mjs:135-137, warden/src/clock/batch.mjs:114-116, warden/src/clock/run.mjs:178-182, warden/src/clock/run.mjs:17-22.

send() returns { ok: false, reason: "gas-estimate-too-large", gas } when the estimate exceeds MAX_TX_GAS (15M). In writeCheckInChunk, :114-116 catches every reason that is not reverted-on-simulate and returns it as aborted. run.mjs:178-182 then stops the whole run and returns.

So the one failure that the shrink loop is structurally perfect for -- a chunk that is too large -- is the one it does not shrink. It aborts instead, and aborts identically on the next run, because nothing about the queue has changed.

The chunk size makes this reachable rather than hypothetical. run.mjs:17-22 says so itself, in the code:

The spec's chunk size. UNVERIFIED against a real full chunk: it comes from arithmetic (about 7k gas per check-in against a 15M ceiling), and only one token existed when this was written, so a 1,500-entry estimate could not be taken.

At 7,000 gas per entry, 1,500 entries is 10.5M and fits. At 10,000 gas per entry it is 15M and does not. The real per-entry cost includes a cold SLOAD of the token struct plus a MetadataUpdate log per token in the second loop (MachineReadableOnly.sol:337-340) -- the comment's own estimate acknowledges it was never measured.

Failure scenario. The collection reaches roughly 1,500 daily active tokens. The 00:05 run assembles a full chunk, estimateContractGas returns above 15M, writeCheckInChunk aborts, runClock returns at :181, and the day's marks and reconcile never run either. Every subsequent night does the same, and the queue grows, which makes the estimate larger, which guarantees it never recovers. The alert reads clock: check-ins aborted (gas-estimate-too-large) and the exit code is 1, so this one is at least loud -- but it is unrecoverable without a code change.

What to do. Treat gas-estimate-too-large in batch.mjs the same way as an unnamed revert: halve and retry, rather than abort. The bisect path at :143-157 already exists and is exactly right for this. It also removes the dependence on CHECKIN_CHUNK being correct, which the comment concedes nobody has measured.

15.10 The Clock decides which days have closed from the box clock, which is the one place CLAUDE.md's rule is not followed

Severity: Low

warden/src/clock/main.mjs:78 (today: utcDay()), warden/src/mcp/tools/checkin.mjs:8, warden/src/clock/run.mjs:166.

CLAUDE.md's check-in rule is explicit: "read the contract's today(), never the box's clock." main.mjs:78 passes utcDay() -- Math.floor(Date.now() / 86_400_000) -- and run.mjs:166 selects rows with q.pendingCredits(today - 1).

The consequence is bounded rather than dangerous, and the bound is the contract's own. If the box clock runs ahead, today - 1 can exceed the chain's today(); batchCheckIn:319 reverts FutureDay(day), ENTRY_ERRORS condemns by day (batch.mjs:27), and every entry for that day is dropped and stays queued for a later night. What to do. Read today() off the contract in main.mjs -- the Clock already has a publicClient at :67 and the ABI at :30 -- and pass that. Then the rule is followed everywhere it applies rather than everywhere but here.

16.1 A Clock run interrupted between broadcast and receipt freezes that token's on-chain record permanently -- and nothing can recover it

Severity: High

warden/src/clock/write.mjs:141-168, warden/src/clock/batch.mjs:123-139, warden/src/clock/reconcile.mjs:69-119, warden/src/mirror/queries.mjs:54-56, warden/src/mirror/schema.sql:36-42, and contracts/src/MachineReadableOnly.sol:283.

Three facts that are each individually reasonable combine into an unrecoverable state.

Fact one -- the write is only durable one side of the wire. write.mjs:141-159 broadcasts, then awaits the receipt, and only run.mjs:169-172 marks the mirror rows written. The comment at write.mjs:19-22 is right that receipt.status === "success" is the only proof -- but the failure it does not cover is the process ceasing to exist between line 150 (the hash is back, the transaction is in the mempool) and line 159. The transaction lands. The mirror never learns.

Fact two -- a landed check-in cannot be reconciled. applyEvents (reconcile.mjs:69-119) handles Rested, Transfer, Rebound, Minted and MarkApplied. It does not handle check-ins, and it could not: the contract's only check-in event is BatchCheckedIn(uint32 fromDay, uint32 toDay, uint256 count) (MachineReadableOnly.sol:283), which carries a count and no token ids at all. Minted and MarkApplied both name their token, which is exactly why an interrupted mint and an interrupted applyMark DO self-heal (run.mjs:142-157, run.mjs:219-223). Check-ins have no such path.

Fact three -- the re-chunk rule condemns by token, not by (token, day). batch.mjs:128 reads String(e.tokenId) === value. DayNotAdvanced is declared DayNotAdvanced(uint256 id) (MachineReadableOnly.sol:276), so its one argument is a token id, and the filter removes every entry for that token from the chunk.

Failure scenario, in order.

  1. Night 1, 00:05. The Clock sends batchCheckIn for day D including token 42. The transaction is broadcast. Before waitForTransactionReceipt resolves the process is gone -- SIGKILL from TimeoutStartSec=600 (see 16.7), an OOM kill, a reboot, an operator's systemctl --user stop. The transaction mines. On chain, token 42's lastDay is now D.
  2. The mirror still has credits(42, D, status='queued').
  3. Night 2. pendingCredits (queries.mjs:54-56) returns (42, D) and (42, D+1), ordered by day. The simulation reverts DayNotAdvanced(42), because D is no longer ahead of the chain's lastDay.
  4. batch.mjs:127-131 drops both rows -- D and D+1 -- because both carry token id 42. Neither is marked written; both stay queued.
  5. Night 3 the chunk carries D, D+1 and D+2 for token 42. Same revert, same filter, all three dropped. This repeats forever.

Token 42 is credited on chain up to day D and never again. The heart is one cell per credited day, so the artwork stops growing at the moment of the crash and every day the agent earns after it is silently discarded. There is no operator recovery short of hand-editing the mirror: credits has no failed state (schema.sql:40 -- only queued and written), nothing ever deletes a credit row, and stuckMints / stuckMarkOrders have no counterpart for credits, so the nightly summary reports these as dropped and the run exits zero (clock/main.mjs:97-102 fails the run on aborted or stuck, not on dropped). The systemd unit records success.

This is reasoned from the code, not demonstrated -- I did not kill a live run. Every step of it is a line I have read, and the precondition is ordinary (see 16.7), but I have not reproduced it end to end.

What to do. The mirror cannot learn about a landed check-in from the chain's events, so it has to learn it from the chain's state: before condemning an entry on DayNotAdvanced, read viewOf(tokenId).lastDay and, if it is at or past the entry's day, mark that ONE row written rather than dropping it -- the same shape as the TokenExists and MarkAlreadyApplied handling that already exists two functions away. Separately, batch.mjs:128 should condemn (tokenId, day) rather than every row for the token, so one stale day cannot take the good ones with it; DayNotAdvanced names only the id, so pair it with the entry's own day. Third, persist the transaction hash on the rows before broadcasting, so a restart can ask the chain what happened rather than inferring it. And give credits a failed state with an attempt counter, so a row that cannot be written stops being silent.

16.6 A PM2 restart between the mint's database commit and x402 settlement gives away a free mint, and the 5-second grace written to prevent it is dead code

x402's exact scheme runs the authorization flow: verify before the handler, settle after it returns -- x402.mjs:78-84 documents this and it is what cancelSettlementOnRefusal exists to exploit. So the ordering on a successful mint is:

  1. payment verified (nothing has moved),
  2. the handler runs and q.transact() commits the mints and tokens rows (mint.mjs:95-98) -- durable, and the Clock will mint that token at 00:05,
  3. @x402/mcp submits the EIP-3009 authorisation and the USDC moves.

Anything that ends the process between 2 and 3 leaves a paid-for row that was never paid for. One free mint, or one free Mark up to $1,250.00 by the same path through upgrade.mjs:157 onward.

This is not attacker-triggerable as far as I can see -- nothing exposed lets a caller force a restart, max_memory_restart: "512M" is hard to reach behind a 64 KB body cap, and the solve is a child process with its own heap. It is an operator-timing bug, and at current volume it is unlikely; at launch volume, with a deploy during a burst, it is not.

16.7 TimeoutStartSec=600 with no SIGTERM handler makes 16.1's precondition routine rather than exotic

Severity: Medium

warden/deploy/mro-clock.service:20, warden/src/clock/write.mjs:159, warden/src/clock/main.mjs:62-103.

TimeoutStartSec=600

The comment above it reasons that "a run still going after that is stuck, and killing it is correct because the next run re-reads the world rather than resuming a plan". The first half is a fair judgement. The second half is the assumption 16.1 breaks: the next run does re-read the world, and for check-ins the world does not tell it what happened.

The Clock has no SIGTERM handler at all -- clock/main.mjs installs none, unlike main.mjs:273-274 which installs two for the Warden -- so systemd's SIGTERM at 600 seconds terminates Node immediately, wherever it is.

How a run reaches 600 seconds. Every write is sequential and each one awaits its receipt (write.mjs:159); Base blocks are two seconds, so a confirmed transaction costs roughly two to six seconds. Mints are one transaction each (run.mjs:113-163) and Marks are one each (run.mjs:201-240). A day with 150 mints is already at or past the timeout before check-ins are attempted, and CLAUDE.md's own planning figure for check-ins is 1,000 agents. The timeout is therefore not a backstop for a hung run -- it is the expected outcome of a busy day, and it lands the process squarely in the window described in 16.1.

What to do. Handle SIGTERM: stop starting new sends, finish awaiting the receipt for the one in flight, mark that row, then exit -- which shrinks the dangerous window from "the whole run" to "one receipt". Raise TimeoutStartSec to something derived from the expected queue depth, and add TimeoutStopSec so the graceful stop has room. Then fix 16.1 anyway, because a reboot gives no warning at all.

What to do. Wrap the Clock's entry point in an advisory lock on a fixed path (flock on a file beside the mirror, taken before startRun() and released at exit) and refuse to start when it is held, naming the holder. That protects the manual path, the rehearsal path and the timer path with one mechanism, and it costs one file descriptor.

What blocks a mainnet deploy

Eleven findings survived verification at Critical or High. In rough order of what would cost most:

  1. 14.1 (Critical) -- a mint or a Mark is committed to the mirror before settlement is attempted and nothing reads the settlement result, so a failed settlement leaves a free token or a free Vessel. Demonstrated, not reasoned.
  2. 14.3 (Critical) -- the mirror's key binding never converges with the chain's, so a seller keeps upgrade and seed on a sold token forever and a rebound buyer is locked out of both forever.
  3. 16.4 (High) -- no deploy script asserts block.chainid, and the only deployer variable is one the schema itself calls a throwaway; that key becomes the permanent owner.
  4. 16.3 (High) -- the facilitator client is built with no authentication and there is no configuration slot for a CDP key, so no agent can pay on mainnet. Fails closed, but the piece cannot be entered.
  5. 13.1 (High) -- one captured signed request is replayable for up to five minutes; reproduced independently.
  6. 15.3 (High) -- the spec's "only with a paid settlement" is false, and a stolen Clock key can end the piece permanently. Argues for lowering supplyCap and rehearsing setWarden rotation BEFORE the deploy.
  7. 16.1 (High) -- a Clock killed between broadcast and receipt freezes that token's check-in record permanently, because the re-chunk rule condemns by token id rather than by (token, day).
  8. 15.2 (High) -- the same seam from the other direction: an uncaught receipt wait plus attempts-exhausted wedges the WHOLE credit queue.
  9. 15.1 (High) -- the key-generation script hands the Clock's private key to cast as argv[3], readable from /proc/<pid>/cmdline by any local uid.
  10. 12.1 (High) -- a sold token stays under the seller's key, who can permanently close a Mark pair on it and spend its seed. Needs a Warden change; the contract is permanent.
  11. 13.2 (High) -- 20,000 unauthenticated requests fill the 10,000-key table and permanently close registration, which is how the reference client gets in.

Two Mediums are hard blockers by construction even though they are not High. 15.5 / 16.2 (no DEPLOY_BLOCK entry for chain 8453) throws on the first mainnet Clock run, after that run has already written to the chain, and does so every night until someone edits the file. 14.5 (nothing checks MRO_CHAIN_ID against the RPC) is the single most likely misconfiguration in a mainnet cutover, and it is what would let testnet USDC be quoted against mainnet writes.
